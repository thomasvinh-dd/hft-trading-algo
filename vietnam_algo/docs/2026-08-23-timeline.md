## Bug Fix #1 — Window Mismatch in Rebuy Eligibility

`corporate_action_exit_rebuy_allowed` originally used only
`corporateActionSellWindowDays=1`. But exit decisions get made via the wider
`corporateActionHighRiskSellWindowDays=5` window. So an exit caused by a
pure-standard event at sessions_until=2 was being *decided* via the wide
window but the *rebuy check* (narrow window) saw no upcoming event and silently
dropped it.

Fix: union-window lookup in both `corporate_action_exit_rebuy_allowed` and
`next_corporate_action_ex_date`.

```text
Before: max(sellWindowDays, highRiskSellWindowDays) = max(1, 5) = 5
        BUT rebuy check used sellWindowDays=1
After:  rebuy check uses max(sellWindowDays, highRiskSellWindowDays)
```

## Bug Fix #2 — Risk Classifier Over-flagging

`corporate_action_risk_type` matched on `name + note + title` with bare terms
like `"phát hành"` and `"chuyển đổi"`. The `title` field is a long regulatory
summary that frequently mentions unrelated events on the same ex-date
(e.g. cash-dividend events whose title says "phát hành cổ phiếu để tăng vốn
cổ phần từ nguồn vốn chủ sở hữu"). The substring `"phát hành"` matched and
events were wrongly flagged high-risk, blocking their post-CA rebuy.

Fix:
- Inspect only `name + note`, never `title`
- Use specific multi-word terms: `"phát hành thêm"`, `"trái phiếu chuyển đổi"`,
  etc. (not bare `"phát hành"`)

Verified against the live dataset of 13,821 events:

```text
high: 572
standard: 13249
empty text: 0
```

After the two fixes:

```text

return: 192.77% → 206.16%
max DD: -25.91% → -23.22%
trades: 1399 → 1406
```

## Signal-Based Rebuy (Post-CA)

User asked: "delay 3 or 6 days is too fit to the current state of market;
we need some method that rebuy correctly due to some signal".

Built a signal framework mirroring the existing fixed-day delay. Five
modes:

```text
recovery      — current close >= min_close_since_ex * (1 + threshold)
stabilization — range of last K closes < threshold
new_high      — current close >= max(closes since ex)
ma_cross      — current close > N-day MA of post-ex window
no_new_low   — current close >= min(last K closes)
combined     — recovery AND stabilization
```

Plus a time fallback max_days so the rebuy never stays queued forever.

Best result in the in-sample backtest (note: post-CA signal modes here used
`PreExitDays=5`; the gold 236.95% line uses the legacy `PreExitDays=1`
behavior — see drift note at bottom of file):

```text
recovery r=0.008:      219.49% return
ma_cross MA=3:        218.30%
combined:             190.29%
new_high:             202.57%
fixed delay=6 (gold): 236.95%
no CA:                222.39%
```

Honest read: fixed delay=6 wins on this dataset, but the path is spike-y
(delay=3 = 224%, delay=5 = 202%, delay=6 = 237%). The signal-based 219.49% is
+18.8pp better than "fire ASAP" (200.66%) but 17pp lower than the
fixed-delay sweet spot. In principle the signal-based is more robust to
future market regime shifts because it responds to actual price action
rather than calendar days.

## ma_cross Was Silently Broken

Audit caught a third bug: `evaluate_post_ca_rebuy_signal` listed `ma_cross` in
the docstring and CLI choices but had no `rebuy_signal_ma_cross` helper and no
`ma_cross` branch — it fell through to "unknown_mode" → returns False. So
setting `--corporate-action-rebuy-signal-mode ma_cross` produced **zero** signals;
the rebuy only fired when the time fallback kicked in (max_days).

Fixed:

```python
def rebuy_signal_ma_cross(closes_window, ma_period):
    if len(closes_window) < ma_period:
        return False
    ma = sum(closes_window[-ma_period:]) / ma_period
    return closes_window[-1] > ma
```

End-to-end smoke test now passes all 6 modes:

```text

ma_cross:        OK
no_new_low:      OK
combined:        OK
```

## 2026-08-24 Follow-up — CA Price-Basis Handling and Rebuy Sweep

Today's work clarified how the strategy should operate when the data provider
updates historical prices after a corporate action.

### Provider-Adjusted History Policy

The project will **not** calculate corporate-action price adjustments locally.
The price provider is expected to return a revised, adjusted, continuous
history after an ex-date. The algorithm must refresh that history and rebuild
the momentum inputs from the refreshed data.

Example scenario:

```text
Before provider refresh:
  2025-12-04 close: 280,500
  2025-12-05 close: 142,800

After provider refresh:
  historical pre-ex prices are adjusted by the provider
  so the series is continuous across 2025-12-05
```

The current price loader treats the cached provider values as the canonical
series. There is no local split, bonus, rights, or dividend adjustment in the
momentum engine. This is correct only if the provider data is consistently
adjusted.

The EOD pipeline already has the correct broad ordering when price updating is
enabled:

```text
1. Sync corporate actions.
2. Refresh price history with --update-prices.
3. Rebuild the liquid universe.
4. Re-run momentum, relative strength, SMA, volatility, and ranking logic.
5. Generate next-session orders.
```

`daily_engine.py:update_dataset` calls `sync_prices(..., skip_existing=False)`
when `EngineConfig.updatePrices` is enabled, so the provider can replace the
old cached history with its newly adjusted history. The remaining reliability
gap is that the bot does not yet perform a targeted affected-symbol refresh or
validate continuity before generating orders.

### CA Guard Versus Momentum Data

The corporate-action guard and provider history refresh solve different
problems:

```text
CA guard:
  protects an open position from an ex-date event and queues a rebuy.

Provider refresh:
  prevents a false price discontinuity from corrupting momentum indicators.
```

If the guard sees VIC's event before the ex-date, the position exits with
`corporate_action_exit`, not `stop_loss` or `trailing_stop`. However, the guard
alone does not repair a discontinuous price series used by ranking, momentum,
SMA, volatility, downside volatility, breakout, or market-relative calculations.

If the provider has not yet revised the history, a move such as
`280,500 -> 142,800` is incorrectly interpreted as a real approximately 49%
loss by the momentum model. Therefore price refresh must complete before the
next order-generation run after a CA.

### Decision Going Forward

For the current implementation, use the simple bounded policy rather than the
compound signal policy:

```text
corporateActionRebuySignalMode=fixed_delay
corporateActionRebuyDelayDays=2
```

This is a practical compromise: it avoids the known immediate VIC post-ex
spike while remaining simpler and more predictable than signal combinations.
The delay-6 result has the highest return in the current comparable sweep, but
also has the deepest drawdown and should be treated as an in-sample result,
not as proof of future superiority.
